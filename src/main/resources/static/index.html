Prerrequisitos
  • Java 17 instalado y en el PATH del sistema (java -version debe mostrar 17.x)
  • XAMPP con el servicio MySQL activo (Apache es opcional)
  • Base de datos inventario creada en MySQL (se crea una sola vez)
  • No se necesita Maven instalado — el proyecto incluye mvnw.cmd (Maven Wrapper)
Levantar la aplicación — primera vez

Estos pasos se ejecutan una sola vez para configurar la base de datos.

1. Iniciar MySQL desde XAMPP Control Panel
Abrir XAMPP → hacer clic en Start en la fila de MySQL. El indicador se vuelve verde.
2. Crear la base de datos en phpMyAdmin
http://localhost/phpmyadmin
Ir a Nueva → escribir inventario → clic en Crear. Solo se hace una vez.
3. Abrir terminal en la carpeta del proyecto
cd C:\proyecto\task-manager\task-manager
4. Ejecutar la aplicación
mvnw.cmd spring-boot:run
Spring Boot crea todas las tablas automáticamente gracias a ddl-auto=update. El usuario admin se crea solo.
Uso normal (día a día)
Iniciar la app
  1. Abrir XAMPP → Start MySQL
  2. Abrir terminal en la carpeta del proyecto
  3. Ejecutar:

  4. Esperar hasta ver:
    Started TaskManagerApplication
  5. Abrir:
    http://localhost:8080

Detener procesos — comandos en terminal
Detener la aplicación Spring Boot
En la terminal donde está corriendo:
Ctrl + C
Presionar Ctrl+C una vez. Windows preguntará "¿Desea terminar el archivo por lotes?" → responder S y Enter.
Si la terminal se cerró y el puerto 8080 sigue ocupado
Buscar el proceso que ocupa el puerto:
netstat -ano | findstr :8080
Ver la columna PID (el número al final) y matar ese proceso:
taskkill /PID 12345 /F
Reemplazar 12345 con el PID real que mostró el comando anterior.
Detener MySQL desde XAMPP
XAMPP Control Panel → clic en Stop en la fila de MySQL.
Siempre deten Spring Boot antes de apagar MySQL, de lo contrario la app lanzará errores de conexión.
Si necesitas limpiar y recompilar
mvnw.cmd clean package
Genera un JAR ejecutable en target/task-manager-0.0.1-SNAPSHOT.jar
java -jar target/task-manager-0.0.1-SNAPSHOT.jar
Alternativa para ejecutar sin Maven (por ejemplo en un servidor).

Fortalezas
Arquitectura en capas correcta
Controller → Service → Repository → Entity. Separación clara de responsabilidades. Los DTOs protegen el modelo interno.
Spring Security bien implementado
Roles ADMIN/SUPERVISOR/VENDEDOR con restricciones por endpoint. BCrypt para contraseñas. Sesión con formulario de login personalizado.
Manejo correcto de transacciones
@Transactional en operaciones que modifican múltiples tablas. Las ventas son atómicas: si falla el stock, nada se persiste.
Módulo de proveedores con análisis real
Promedios móviles, regresión lineal simple con R², alertas inteligentes con cooldown, score multi-factor. Válido como feature de producto comercial.
Cumplimiento fiscal colombiano
IVA (0%/5%/19%) por producto, resolución DIAN, NIT con DV, numeración secuencial sincronizada. Pocas apps pequeñas implementan esto.
Escalabilidad inmediata a producción
Cambiar H2 a PostgreSQL solo requiere 3 líneas en application.properties. La arquitectura no necesita modificarse.
Debilidades actuales
Sin pruebas automatizadas
No hay tests unitarios ni de integración. En producción esto es un riesgo alto: cualquier cambio puede romper funcionalidad sin saberlo.
Sin manejo de concurrencia en cajas
Si dos vendedores venden el mismo producto al mismo tiempo, el stock puede quedar incorrecto. Falta @Version (optimistic locking) en Product.
Credenciales en texto plano
El usuario root de MySQL sin contraseña y la URL de conexión están en application.properties. En producción esto es un fallo de seguridad crítico.
Frontend monolítico
Un solo archivo app.js de ~1000 líneas que crece con cada módulo. Difícil de mantener a largo plazo. No hay separación de componentes.
Sin paginación en listas
Todos los endpoints devuelven la lista completa. Con miles de productos o cotizaciones, las páginas se volverán lentas.
Sin logging estructurado
No hay registros de auditoría de quién hizo qué y cuándo. En un sistema de ventas esto es indispensable para soporte y trazabilidad.
Recomendaciones por prioridad
Prioridad ALTA — antes de lanzar

1. Mover credenciales a variables de entorno
Usar SPRING_DATASOURCE_PASSWORD en el sistema en lugar de en el archivo de código.

2. Añadir @Version a Product
Un campo @Version Long version previene condiciones de carrera en actualización de stock.

3. Respaldo de base de datos
Programar un dump de MySQL periódico con mysqldump inventario > backup.sql.

Prioridad MEDIA — próximos sprints

4. Tests de integración
Al menos 1 test por flujo crítico: crear venta, verificar descuento de stock, generar alerta.

5. Paginación en API
Cambiar findAll() por findAll(Pageable) en productos, ventas y cotizaciones.

6. Separar app.js en módulos
Ya se inició con proveedores.js. Continuar con ventas.js, inventario.js, etc.

Prioridad BAJA — mejoras futuras

7. Migrar frontend a React o Vue
El backend REST ya está listo para consumirse desde un SPA moderno sin cambios.

8. Notificaciones por email
Spring Mail + Mailgun para enviar alertas de stock bajo y predicciones de precio al ADMIN.

9. Deploy en la nube
El JAR puede desplegarse en Railway, Render o EC2 con un cambio de datasource a PostgreSQL.

Conclusión

Esta aplicación está en un nivel intermedio-profesional real. No es un proyecto de estudio — tiene lógica de negocio concreta, cumplimiento fiscal, análisis predictivo y control de acceso por roles. Muchos sistemas comerciales pequeños para tiendas o PYMEs colombianas no tienen la mitad de estas funcionalidades.

Lo que la separa de una aplicación 100% enterprise es principalmente la falta de pruebas automatizadas, un manejo más robusto de errores concurrentes y configuración segura de credenciales.

Con las mejoras de prioridad alta implementadas, esta aplicación podría venderse o desplegarse para un negocio real sin problemas.
